# Правила совместной работы команды

Читают координатор (главный Claude, навык `/lesson-team`) и все агенты. Коротко: один исполнитель, несколько проверяющих, каждая проверка привязана к версии файлов.

## Роли и права

| Агент | Что делает | Меняет файлы? |
|---|---|---|
| `lesson-methodist` | Учебный замысел и сценарий | Нет. Возвращает текст сценария |
| `subject-reviewer` | Предметная правильность | Нет в проекте. Bash — только чтобы запустить пример во временной папке |
| `lesson-builder` | Реализация и исправления | **Да — единственный**, и только разрешённые постановкой файлы |
| `language-editor` | Языки, термины, озвучка | Нет. Возвращает точные замены |
| `learning-reviewer` | Подтверждает ли урок понимание; аналитика и достижения | Нет |
| `ux-reviewer` | Урок глазами ученика | Нет |
| `qa-tester` | Реальные браузерные и функциональные проверки | Пишет **только отчёты** в `work/lesson-team/<run-id>/` через QA-скрипты. Уроки и исходники не меняет. Не «только чтение»: у него есть Bash |

Отдельного агента-пересказчика нет: отчёты объединяет координатор.

## Постановка задачи

Координатор начинает каждый запуск с постановки по шаблону `shablon-postanovki.md` и сохраняет её в `work/lesson-team/<run-id>/brief.md`. Режим «только проверка» запрещает менять проверяемые файлы. Просьба о новом тестовом варианте — всегда новый файл с уникальным именем.

## Версии

- Перед проверкой координатор фиксирует версию: `node tools/qa/lesson-team/version.mjs <файлы> --save work/lesson-team/<run-id>/versions/<метка>.json`.
- В шапке каждого отчёта — эта версия.
- После правок версия новая; проверки затронутых частей повторяются. Старый `passed` её не подтверждает.
- Во время браузерного QA файлы урока не редактируются: перезагрузка Vite обесценит прогон. QA-скрипт сам сверяет хеши до и после и ставит `blocked`, если файл изменился.

## Параллельность

- Одновременно — не больше трёх субагентов.
- Параллельно запускаются только независимые проверки **одной зафиксированной версии** (например, язык + обучение + UX).
- Исполнитель работает один. Одновременное редактирование одного файла несколькими агентами запрещено. Если когда-нибудь понадобится параллельная реализация — только в раздельных файлах или изолированной рабочей копии (`isolation: worktree`).

## Передача контекста субагенту

Субагент не видит историю чата и навыков координатора. Каждое поручение содержит:

1. Цель поручения одной фразой и режим (сценарий / реализация / проверка / исправление).
2. Путь к постановке `work/lesson-team/<run-id>/brief.md` и к профилю модуля `docs/lesson-team/moduli/<модуль>.md`.
3. Целевые файлы и что в них можно менять (для проверяющих — «ничего»).
4. Версию (`v-…`) и пути к нужным материалам: сценарий, описание, отчёты QA, скриншоты.
5. Нужные правила: `docs/lesson-team/obshchie-trebovaniya.md`, `format-otchyotov.md`, и только относящиеся к задаче справочники (для HTML — указанные в профиле файлы навыков).
6. Ожидаемый формат ответа (из файла агента) и куда координатор сохранит результат.

Не отправлять агенту весь проект: только относящиеся к его задаче материалы.

## Отчёты запуска

`work/lesson-team/<run-id>/` (создаёт `node tools/qa/lesson-team/new-run.mjs --slug <кратко>`):

```
brief.md                постановка
versions/<метка>.json   зафиксированные версии файлов
01-methodist.md …       ответы агентов (номер — порядок в запуске)
qa/<…>/report.json|md   отчёты QA-скрипта, events.jsonl, shots/
summary.md              сводка координатора: статусы, нерешённое
```

Каталог `work/lesson-team/` исключён из git собственным `.gitignore`. Ничего не коммитить автоматически. Временные отчёты не класть в папки уроков.

## Объединение замечаний и повторные проверки

1. Собрать замечания всех проверяющих, убрать дубли, разделить: подтверждённые / предположения / вкус.
2. Противоречия между агентами решает координатор по приоритету источников (профиль → `CLAUDE.md` → навыки → бриф); спорное, но существенное — вопрос пользователю.
3. Исполнитель получает один нумерованный список и правит последовательно.
4. Повторяются только проверки затронутых частей и связанные сценарии QA — после новых изменений, ошибок или нерешённых замечаний. Не больше двух кругов «исправить → перепроверить» без пользователя: дальше — отчёт с нерешённым.

## Когда спрашивать пользователя

Только при существенной нехватке данных или противоречии, которое мешает корректной работе: нет профиля модуля и неясны технические ограничения; тема отсутствует в плане; задача требует нарушить контракт платформы; запрос противоречит прямому указанию заказчика. Творческие и технические решения команда принимает сама. Сценарий ждёт утверждения только по прямой просьбе.
