# Правила совместной работы команды

Читают координатор (главный Claude, навык `/lesson-team`) и все агенты. Коротко: один исполнитель, несколько проверяющих, содержание проверяется до реализации, каждая проверка привязана к версии файлов, урок передаётся QA-команде заказчика со статусом «готов к QA».

## Цель и бюджет

Стандартный запуск `/lesson-team <задача>` (без параметров) за 60–90 минут готовит содержательно проработанный, работающий урок и передаёт его QA-команде заказчика. Это ориентир для типового урока на существующем каркасе, а не повод объявлять незавершённое готовым.

Главный приоритет — качество обучения: понятные объяснения, правильные примеры, интересные действия, самостоятельное применение, качественные тексты на всех языках. Время экономится на дублировании и лишних прогонах, а не на содержании.

Если урок требует новой механики или у модуля нет каркаса, координатор выделяет эту подготовку отдельно и сообщает, на сколько она удлиняет срок. Учебная цель молча не упрощается.

## Стандартный процесс

1. **Постановка** (координатор): тема, аудитория, изученное, профиль модуля, границы изменений.
2. **Сценарий** (`lesson-methodist`): цели, последовательность объяснений, задания с ожидаемыми ответами, типичные ошибки, подсказки, самостоятельная проверка, итоговые данные.
3. **Проверка сценария, параллельно:** предмет (`subject-reviewer`), качество заданий (`learning-reviewer`), языки (`language-editor`). Один объединённый список → методист вносит **до реализации**.
4. **Сборка** (`lesson-builder`) из существующих компонентов и сборщика по окончательному сценарию.
5. **Сверка содержания и реализации и короткая техническая проверка, параллельно:** `learning-reviewer` (сверка со сценарием), `language-editor` (тексты реализации), `qa-tester` (короткая техническая проверка). Один объединённый список → исполнитель → повтор только затронутого.
6. **Передача** QA-команде заказчика по `shablon-peredachi.md`. Статус — «готов к QA».

## Роли и права

| Агент | Что делает | Меняет файлы? |
|---|---|---|
| `lesson-methodist` | Учебный замысел и сценарий | Нет. Возвращает текст сценария |
| `subject-reviewer` | Предметная правильность сценария и реализации | Нет в проекте. Bash — только чтобы запустить пример во временной папке |
| `lesson-builder` | Сборка и исправления | **Да — единственный**, и только разрешённые постановкой файлы |
| `language-editor` | Языки, термины, озвучка — в сценарии и в реализации | Нет. Возвращает точные замены |
| `learning-reviewer` | Качество заданий в сценарии; сверка реализации со сценарием, учёт и итоговые данные | Нет |
| `ux-reviewer` | Урок глазами ученика — **только по просьбе** (интерфейс, телефон) | Нет |
| `qa-tester` | Короткая техническая проверка; полный QA — только по прямой просьбе | Пишет **только отчёты** в `work/lesson-team/<run-id>/` через QA-скрипты. Уроки и исходники не меняет. Не «только чтение»: у него есть Bash |

Отдельного агента-пересказчика нет: отчёты объединяет координатор.

## Готовые компоненты, а не новый код

- Исполнитель собирает урок из того, что уже есть в модуле: канон, помощники, механики, сборщик (раздел «Готовые компоненты и сборка» профиля модуля). Общий код вручную заново не пишется.
- Новая библиотека не начинается «на всякий случай»: сначала выясняется, чего действительно не хватает сценарию.
- Готовые механики не ограничивают сценарий: история, примеры и действия подбираются под тему, урок не превращается в однотипную викторину.
- Не хватает механики — исполнитель называет это в отчёте, координатор выделяет её отдельной задачей и сообщает пользователю о сроке.

## Кто что проверяет

| Проверка | Кто | Когда |
|---|---|---|
| Сборка, синтаксис, наличие текстов и переводов | `lesson-builder` (самопроверка) | после сборки и каждой правки |
| Предмет, качество заданий, языки сценария | `subject-reviewer`, `learning-reviewer`, `language-editor` | шаг 3, до реализации |
| Сверка реализации со сценарием, тексты реализации | `learning-reviewer`, `language-editor` | шаг 5 |
| Короткая техническая проверка: основной путь на русском в быстром режиме, основной ввод и сохранение результата, однократное завершение | `qa-tester` | шаг 5 |
| Полная матрица устройств, языков, ошибок и состояний | **QA-команда заказчика**; `qa-tester` — только по прямой просьбе | после передачи |

Автоматически не запускаются: многочасовые браузерные прогоны, сотни скриншотов, полный QA исполнителем, повторные проверки всеми агентами. Исполнитель не делает полных прогонов, даже если поручение их просит (в запусках 18–19.10.2026 полный QA шёл дважды и занимал 1,5–3,5 часа на урок).

## Постановка задачи

Координатор начинает каждый запуск с постановки по шаблону `shablon-postanovki.md` и сохраняет её в `work/lesson-team/<run-id>/brief.md`. Режим «только проверка» запрещает менять проверяемые файлы. Просьба о новом тестовом варианте — всегда новый файл с уникальным именем.

## Версии

- Перед проверкой реализации координатор фиксирует версию: `node tools/qa/lesson-team/version.mjs <файлы> --save work/lesson-team/<run-id>/versions/<метка>.json`.
- В шапке каждого отчёта — эта версия. После правок версия новая; старый `passed` её не подтверждает.
- Во время браузерного прогона файлы проверяемого урока не редактируются. QA-скрипт сам сверяет хеши до и после и ставит `blocked`, если файл изменился.
- Плеер подключает все уроки через `import.meta.glob('/lessons/*/*.jsx')` (`src/shared/catalog.js`), и общий dev-сервер с HMR перезагружает страницу при записи любого файла в `lessons/`. Поэтому QA идёт со своим сервером: `run.mjs --serve` (свободный порт, без HMR).

## Параллельность

- Одновременно — не больше трёх субагентов. Один исполнитель на урок.
- Параллельно — независимые проверки сценария (шаг 3) и проверки одной зафиксированной версии (шаг 5).
- Несколько уроков сразу — у каждого своя рабочая копия `.claude/worktrees/lt-<run-id>/`:
  - `node tools/qa/lesson-team/wt.mjs create --run <run-id>` — копия от HEAD плюс незакоммиченные и новые файлы, `node_modules` ссылкой;
  - `wt.mjs status` — что изменено; `wt.mjs sync --changed` — перенос в основную копию (останавливается, если файл в основной копии изменился после создания копии); `wt.mjs remove` — удалить копию.
  Один урок делается в основной копии, без рабочей копии.
- Одновременное редактирование одного файла несколькими агентами запрещено.
- Фоновые ожидания — только с пределом времени; свои фоновые процессы агент останавливает до завершения.

## Передача контекста субагенту

Субагент не видит историю чата и навыков координатора. Каждое поручение содержит:

1. Цель поручения одной фразой и режим (сценарий / проверка сценария / сборка / сверка / исправление).
2. Путь к постановке `work/lesson-team/<run-id>/brief.md` и к профилю модуля `docs/lesson-team/moduli/<модуль>.md`.
3. Целевые файлы и что в них можно менять (для проверяющих — «ничего»).
4. Версию (`v-…`) и пути к нужным материалам: сценарий, отчёты.
5. Нужные правила: `docs/lesson-team/obshchie-trebovaniya.md`, `format-otchyotov.md`, и только относящиеся к задаче справочники (для HTML — указанные в профиле файлы навыков).
6. Ожидаемый формат ответа (из файла агента) и, для тестировщика, объём: «короткая техническая проверка» или «полный QA».

Не отправлять агенту весь проект: только относящиеся к его задаче материалы.

## Отчёты запуска

`work/lesson-team/<run-id>/` (создаёт `node tools/qa/lesson-team/new-run.mjs --slug <кратко>`):

```
brief.md                постановка
scenario.md             окончательный сценарий
versions/<метка>.json   зафиксированные версии файлов
01-methodist.md …       ответы агентов (номер — порядок в запуске)
qa/<…>/report.json|md   отчёты QA-скрипта
peredacha.md            передача QA-команде заказчика (shablon-peredachi.md)
```

Каталог `work/lesson-team/` исключён из git собственным `.gitignore`. Ничего не коммитить автоматически. Временные отчёты не класть в папки уроков.

## Объединение замечаний и повторные проверки

1. Собрать замечания, убрать дубли, разделить: подтверждённые / предположения / вкус.
2. Противоречия между агентами решает координатор по приоритету источников (профиль → `CLAUDE.md` → навыки → бриф); спорное, но существенное — вопрос пользователю.
3. Исполнитель (или методист на шаге 3) получает **один** нумерованный список и правит последовательно.
4. Повторяются только проверки затронутого содержания или поведения (таблица в `SKILL.md`, раздел 3). Не больше двух кругов «исправить → перепроверить» без пользователя: дальше — передача с нерешённым.
5. Вкус и необязательные улучшения в круги не входят — только в передачу.

## Статус урока

- «готов к QA» — урок передан QA-команде заказчика; пока она не завершила приёмку, другого статуса нет.
- Блокирующая ошибка, найденная короткой проверкой и не исправленная, — урок не передаётся как «готов к QA»; передача называет ошибку.

## Когда спрашивать пользователя

Только при существенной нехватке данных или противоречии, которое мешает корректной работе: нет профиля модуля и неясны технические ограничения; у модуля нет каркаса урока; тема отсутствует в плане; задача требует нарушить контракт платформы; запрос противоречит прямому указанию заказчика. Творческие и технические решения команда принимает сама. Сценарий ждёт утверждения только по прямой просьбе.
